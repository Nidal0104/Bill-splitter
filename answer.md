1. HOW TO RUN
No installation is required. The project is entirely vanilla HTML, CSS, and JavaScript with zero external dependencies or build steps.
Steps on a fresh machine:

Download or clone the project folder containing these four files: index.html, styles.css, script.js, README.md — all in the same directory.
Open index.html directly in any modern browser by double-clicking the file or dragging it into a browser tab.

Live Server (optional): If using VS Code, the Live Server extension (Ritwick Dey) can be used for convenience — right-click index.html → "Open with Live Server". It serves the file at http://127.0.0.1:5500. This is not required; it only adds auto-reload on file changes during development.
Browser requirement: Any evergreen browser — Chrome 90+, Firefox 88+, Safari 14+, Edge 90+. No polyfills needed. The app uses no cutting-edge APIs; standard DOM events, CSS custom properties, and basic arithmetic cover the entire feature set.
Deployment: bill-splitter-tau-inky.vercel.app

2. STACK & DESIGN CHOICES
A) Why vanilla HTML/CSS/JS?
The project scope is a single-screen calculator with no routing, no shared state across components, no data fetching, and no build pipeline requirements. Introducing a framework like React would add overhead — a virtual DOM, JSX compilation, a bundler — for a problem that is entirely solved by a few DOM event listeners and arithmetic functions. Vanilla JS keeps the execution model transparent: an input event fires, a pure function runs, three text nodes update. There is nothing hidden in a reconciler or reactive system. For a project of this scope, framework abstraction is cost without benefit.
B) Two specific UI/UX decisions:
Decision 1 — Two-column CSS Grid that collapses to single column at 620px.
The inputs (bill, tip, people) and the outputs (tip amount, total, per-person) are placed in a display: grid; grid-template-columns: 1fr 1fr layout. This was chosen deliberately over stacking them vertically because it allows the user to see both input and output simultaneously while typing — the live-update value proposition is only visible if both panels are in the viewport at once. On screens narrower than 620px, the grid collapses to a single column, inputs appear first, outputs below. The breakpoint was chosen at 620px rather than the common 768px because at 620-768px a two-column card layout still renders comfortably without the cards feeling cramped.
Decision 2 — Errors render only after a field has received non-empty input, not on initial page load.
Each field's validation runs on every input event, but the error string is only assigned to the DOM if the field's current value is non-empty (trimmed). This avoids the jarring pattern where three red error messages appear the moment the page loads because all fields are blank. The mental model for the user is: "errors appear when I've made a mistake, not before I've started." Technically, this is a single ternary per field — const bErr = bTouched && !bRes.valid ? bRes.error : '' — where bTouched is billInput.value.trim() !== ''. The output panel shows dashes (—) rather than Rs 0.00 as the default state, which reinforces that no calculation has happened yet rather than implying the result is zero.

3. RESPONSIVE & ACCESSIBILITY
A) Responsive behavior:
On a 360px mobile screen, the two-column grid collapses to a single column via the @media (max-width: 620px) breakpoint. The inputs card stacks above the outputs card. Card padding reduces from 2rem 1.75rem to 1.5rem 1.25rem. The grand total font size steps down from 2rem to 1.6rem so the number doesn't overflow its container on narrow widths. The three tip preset buttons remain in a flex-wrap: wrap row — on very narrow screens they can wrap to two rows without breaking the layout because they're sized with flex: 1 rather than fixed widths. The currency input prefix badges and suffix badges are inline-flex so they compress naturally without overlap.
On a 1440px desktop screen, the layout stays at max-width: 860px centered in the viewport via margin: auto on the wrapper. The two-column grid renders at roughly 400px per card. Nothing stretches beyond readable line lengths. The app deliberately doesn't go full-width at large breakpoints because a tip calculator doesn't benefit from spanning 1400px — it would create a large expanse of empty space in the output card and widen inputs to an uncomfortable size for a calculator interface.
B) Accessibility:
Implemented: All output values are wrapped in a <section> with aria-live="polite" and aria-atomic="true". This means screen readers announce the updated results after each keystroke without interrupting mid-word if the user is typing quickly — polite waits for the current speech to finish. Each input has a matching <label> associated by for/id, and inline error paragraphs have role="alert" with aria-live="polite" so error messages are announced when they appear without requiring focus to move to the error. All interactive elements — inputs, preset buttons, reset — have visible :focus-visible outlines using a 3px ring in the accent color so keyboard-only users can track their position through the tab order.
Knowingly skipped: A live "per-person amount" announcement that fires on every keystroke was not implemented as a separate, dedicated aria-live region. The current setup announces the entire output section atomically, which means if a screen reader is in the middle of reading "Grand Total Rs 450.00", a new keystroke resets that announcement from the beginning. Implementing a more granular approach — separate aria-live regions per output value with appropriate throttling — was skipped because it would require debouncing announcements to avoid a flood of speech updates on rapid typing, and that complexity was outside the defined scope. It is a real usability gap for screen reader users who type quickly.

4. AI USAGE
Tool used: Claude (Anthropic).
What I asked for: I provided a detailed specification document describing all functional requirements — input validation rules, rounding policy, tip preset behavior, reset behavior, live update requirements, and design constraints (no frameworks, no libraries, Rs currency, vanilla only). I asked Claude to generate the four project files in full.
What AI generated: A complete working implementation across all four files. The structural logic, validation separation, and event wiring were correct. The CSS used a warm editorial palette with a dark output panel, which matched the aesthetic direction.
One concrete example of what I changed and why:
The AI-generated validatePeople function initially only checked Number.isInteger(n) after parsing the string. The problem: Number.isInteger(1.0) returns true in JavaScript, so a user who typed "1.0" would pass validation and be treated as 1 person. That's arguably acceptable in outcome, but the input field is supposed to accept only positive integers — a decimal-point entry should be rejected at the UX level, not silently coerced. I added two things: a keydown listener that calls e.preventDefault() when e.key === '.' (blocking the decimal point from being typed at all), and a string-level check /[.\-]/.test(str) in validatePeople before parsing the number, so pasted input like "2.5" also fails explicitly with the message "Must be a whole number (1 or more)." The original AI code handled the math correctly but didn't consider the input-layer experience — a user who types 2.5 should see an error immediately, not have it silently round to 2.

5. HONEST GAP
The real weakness: The bill input does not prevent a user from typing a number with more than two decimal places (e.g., "123.456"). The calculation will run on it and produce a result like Rs 184.58 (rounded), but the input field itself visually shows 123.456 — an amount that doesn't represent a real currency value. There is no inline message like "Bill amount can have at most 2 decimal places" and no formatting that normalizes the value to 2dp while typing.
Why it's a gap: A tip calculator built for currency should not silently accept sub-cent precision in the bill field. It creates a subtle inconsistency: the input shows three decimals, the output shows two. A user who pastes "1500.999" from somewhere gets a result of Rs 1726.10 with a tip at 15%, which is correct after rounding — but the bill field still reads 1500.999. That's a trust problem even if the math is sound.
How I would fix it with one more day: On the blur event of the bill input, I'd format the value to exactly two decimal places using parseFloat(billInput.value).toFixed(2) and write it back into the field — but only if the value is valid (to avoid formatting an empty or invalid field). During typing I'd leave it unformatted so the user isn't fighting auto-correction mid-entry. I'd also add a step="0.01" attribute (it's currently step="any") and pair it with a regex check in validateBill that rejects more than two decimal places with a clear inline message. This makes the validation complete at both the input level and the message level.
